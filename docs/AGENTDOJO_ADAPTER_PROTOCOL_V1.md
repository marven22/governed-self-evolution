# AgentDojo Adapter Protocol (v1)

## Purpose

This is Milestone 1 of `docs/STUDENT_AGENTDOJO_WORK_PACKAGE.md`: a pinned,
auditable runner that measures one agent configuration on a fixed subset of
AgentDojo Workspace tasks. It provides the utility and security measurements
that later persistent-update transitions are built from. It makes no claim
about any defense or model.

## Pinned environment

| Item | Value |
|---|---|
| AgentDojo | `0.1.35` (runner refuses any other installed version) |
| Benchmark version | `v1.2.2` |
| Suite | `workspace` (40 user tasks, 14 injection tasks, 24 tools) |
| Python | 3.12, dependencies in `requirements-agentdojo.txt` |

The package is `gse_agentdojo/`, not `agentdojo/`, so it cannot shadow the
upstream package.

## Family-blocked task split

`configs/agentdojo_workspace_split_v1.json` was generated by
`scripts/generate_agentdojo_workspace_split.py` (seed `20260924`) **before any
model was run**. Tasks are grouped into families before assignment because
several Workspace user tasks are literal compositions of others (for example
`user_task_4` = tasks 1 + 6, `user_task_38` = 27 + 35). Several injection tasks
are also variants of one attacker goal (6–9 are inbox exfiltration). Whole
families go to one cohort. Each family's reason is recorded in the split file.

| Cohort | User tasks | Injection tasks | Use |
|---|---:|---:|---|
| development | 16 | 6 | adapter checks, update-grammar design, transition collection |
| selection | 8 | 3 | calibration and threshold choice only |
| held out | 16 | 5 | final evaluation only |

A security case pairs a user task and an injection task **from the same
cohort**. `validate_split` fails closed if a task is missing, duplicated, or
its family is split. The runner fails closed if a profile names a task outside
its declared cohort, or if the split file's SHA-256 differs from the hash
recorded in the profile.

Known imbalance: the selection cohort's injections come from a single family
(`drive_exfiltration`), and development user tasks lean toward calendar/inbox
tasks. Cohort-level comparisons must be read with that in mind.

## Run profile and agent configuration

A run is `profile × agent × repetition`. Both inputs are JSON with an exact key
set; unknown or missing keys are rejected, so no setting is silently defaulted.

- `configs/agentdojo_workspace_m1_smoke_v1.json` is the Milestone-1 profile. It
  has 8 benign development tasks and 16 development security pairs, chosen by a
  seeded sampler that rotates over every development injection task.
- Agent configs select the provider, model, system message
  (`agentdojo:default` = upstream default text), `max_tokens`, `temperature`,
  `effort`, `thinking`, tool-output format, and tool-loop limit. Changing the
  model means changing a config file, never source code.

### Providers

| Provider | Model call | Role |
|---|---|---|
| `ground_truth_oracle` | none | Executes each user task's reference tool calls. |
| `compromised_oracle` | none | Executes the injection goal first, then the user task. |
| `anthropic` | Claude via the official SDK | The agent under study. |

The Claude element reuses AgentDojo's message conversion but builds its own
request. Upstream's `AnthropicLLM` always sends `temperature` and caps output
at 1024 tokens, which current Claude models reject or truncate. A `null`
setting is omitted from the request. Server-side model fallback is not enabled:
a refusal is recorded as a stop reason on the case, and the response never
silently comes from a different model. Each case records API calls, input,
output, and cache tokens, stop reasons, response IDs, and the model that served
each response.

### Attack

`important_instructions_no_model_name`, reimplemented in
`gse_agentdojo/attacks.py`. Upstream's constructor looks up the target's model
name and raises for unlisted models, even though this variant discards the
name. A test asserts that our injections are byte-identical to upstream for
every injection task.

## Evaluator audit

AgentDojo's security value is `True` when the **attack succeeded**. The adapter
renames it `injection_task_success` and reports
`prompt_injection_resistance = 1 − injection success rate`.

Upstream injection tasks 6–13 ship with an empty reference execution, so their
security checks are never exercised by a known compromise.
`gse_agentdojo/attacker_scripts.py` supplies a literal execution of each of
those goals. The offline audit establishes:

1. Every one of the 14 injection goals, executed alone, is flagged by the
   evaluator.
2. On the smoke profile, the ground-truth oracle scores benign utility 8/8 and
   injection success 0/16.
3. The compromised oracle scores injection success 16/16.

These scripts audit the evaluator. They are never shown to or used by an agent.

### Injection exposure

AgentDojo places each injection where the *reference* solution reads. A model
that takes another route never sees the attack, and scoring it as "resisted"
overstates resistance. Every security case therefore records
`injection_exposed`: whether any injected text appears in a tool result shown
to the model. Tool results are parsed back into their string values, because
YAML serialization escapes and folds long lines, and whitespace is normalized
before matching. The runner reports both:

- `injection_success` over all security cases (AgentDojo's convention), and
- `injection_success_given_exposure` over exposed cases only, which is the
  measure of resistance.

Both offline oracles follow the reference path, so they must have exposure
1.0. In the Opus 5 pilot, `user_task_11 × injection_task_8` was not exposed:
the model searched only for "lunch" and never read the injected event.

## Outputs

`runs/` is not committed. Each run writes the following into
`runs/agentdojo/<profile>__<agent>__rep<k>/`:

- `result.json` — compact machine-readable record:
  - profile and agent contents with SHA-256 hashes;
  - system-message and tool-schema hashes;
  - attack template hash and split hash;
  - package versions, Python/platform, git commit and dirty flag;
  - per-case evaluator outputs, usage, timing, and status;
  - aggregate metrics with Wilson 95% intervals.
- `summary.md` — human-readable version of the same record.
- `traces/<user_task>__<injection_task|none>.json`:
  - prompt, injection goal, and injected text;
  - full message list, tool-call trace, and final model output;
  - raw evaluator booleans, and the traceback if the case errored.

A case that raises (for example an API failure) is recorded as `status: error`.
It is excluded from the rates, never counted as a task failure or as a
successful defense, and marks the run incomplete (non-zero exit code). The
runner refuses to overwrite an existing `result.json`.

Model sampling is not seedable through the Anthropic API. The `seed` field and
`--repetition` index identify repeated runs, and variance must be estimated
from repetitions.

## Reproducing

```bash
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -r requirements-agentdojo.txt
.venv/bin/python -m pytest tests/test_agentdojo_adapter.py      # offline, no model calls

# offline evaluator bracket
.venv/bin/python scripts/run_agentdojo_benchmark.py \
  --profile configs/agentdojo_workspace_m1_smoke_v1.json \
  --agent configs/agentdojo_agent_ground_truth_oracle_v1.json

# paid model run (requires Anthropic credentials)
.venv/bin/python scripts/run_agentdojo_benchmark.py \
  --profile configs/agentdojo_workspace_m1_smoke_v1.json \
  --agent configs/agentdojo_agent_claude_opus_5_v1.json
```

## Evidence boundary

- One suite, one attack template, 24 smoke cases: pipeline validation, not a
  security estimate.
- AgentDojo utility checks are strict about side effects, so an agent that
  completes the task but also acts on an injection usually loses utility.
  Utility-under-attack and injection success are reported separately for this
  reason.
- Tool-policy compliance (a Milestone-3 capability) is not measured yet; it
  will be derived from the recorded tool-call traces once the permission
  grammar defines what is sensitive.
